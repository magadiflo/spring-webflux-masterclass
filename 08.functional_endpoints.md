## 📖 Introducción

Tradicionalmente, hemos expuesto nuestras APIs utilizando controladores anotados, una aproximación que nos resulta
familiar y funciona muy bien. Por ejemplo, este es un controlador típico con anotaciones como `@GetMapping`:

````java

@GetMapping(path = "/{customerId}")
public Mono<ResponseEntity<CustomerResponse>> getCustomer(@PathVariable Long customerId) {
    return this.customerService.getCustomer(customerId)
            .map(ResponseEntity::ok);
}
````

### 🚀 Functional Endpoints en Spring WebFlux

Sin embargo, `Spring WebFlux` también ofrece una alternativa basada en `programación funcional`:
`los Functional Endpoints`.

Con este enfoque:

- La lógica de enrutamiento se define mediante `funciones puras`, declaradas como beans.
- Los endpoints se configuran explícitamente y se asocian a funciones que manejan la solicitud.
- Podemos incluso definir manejadores de errores dentro del mismo flujo funcional.

Ejemplo de definición de rutas:

````bash
route()
  .GET("/api/v1/customers", handler::getAllCustomers)
  .GET("/api/v1/customers/{customerId}", handler::getCustomer)
  .POST("/api/v1/customers", handler::saveCustomer)
  ...
  .onError(CustomerNotFoundException.class, this::badRequestHandler)
  .build();
````

![01.png](assets/section-08/01.png)

### 📌 Diferencias clave

Al usar `Functional Endpoints`:

- Definimos rutas que redirigen a funciones `(HandlerFunction)` que procesan la solicitud.
- Estas funciones extraen datos, invocan la capa de servicio y retornan respuestas.
- El enrutamiento y la lógica de negocio quedan `separados y más explícitos`.

### ⚠️ Nota importante

> El uso de `Functional Endpoints es completamente opcional`.  
> Podemos seguir utilizando controladores anotados `(@RestController)` si ese enfoque se adapta mejor a nuestras
> necesidades.

### 🌟 Ventajas de los Functional Endpoints

- Mayor flexibilidad: control granular del flujo de solicitudes.
- Apropiado para aplicaciones pequeñas o personalizadas, donde las rutas se definen de forma explícita.
- Separación clara entre enrutamiento y lógica de negocio, lo que facilita el mantenimiento.

## 🧩 Request Handler: `CustomerHandler`

En el `CustomerHandler` vive la lógica equivalente a los métodos del controlador: `recibir la request`,
`validar datos de entrada` y `delegar al servicio`. En otras palabras, el `CustomerHandler` cumple el mismo rol que
un `@RestController`, pero en el mundo de los **functional endpoints**.

### 🧱 Código completo del `CustomerHandler`

````java

@Slf4j
@RequiredArgsConstructor
@Component
public class CustomerHandler {

    private final CustomerService customerService;

    public Mono<ServerResponse> allCustomers(ServerRequest request) {
        return this.customerService.getAllCustomers()
                .doOnNext(customerResponse -> log.info("{}", customerResponse))
                .as(customerResponseFlux ->
                        ServerResponse.ok().body(customerResponseFlux, CustomerResponse.class));
    }

    public Mono<ServerResponse> getCustomer(ServerRequest request) {
        return this.customerService.getCustomer(this.customerId(request))
                .flatMap(customerResponse ->
                        ServerResponse.ok().bodyValue(customerResponse));
    }

    public Mono<ServerResponse> saveCustomer(ServerRequest request) {
        return request.bodyToMono(CustomerRequest.class)
                .transform(CustomerValidator.validate())
                .flatMap(this.customerService::saveCustomer)
                .flatMap(customerResponse ->
                        ServerResponse.status(HttpStatus.CREATED).bodyValue(customerResponse));
    }

    public Mono<ServerResponse> updateCustomer(ServerRequest request) {
        return request.bodyToMono(CustomerRequest.class)
                .transform(CustomerValidator.validate())
                .flatMap(customerRequest ->
                        this.customerService.updateCustomer(this.customerId(request), customerRequest))
                .flatMap(customerResponse ->
                        ServerResponse.ok().bodyValue(customerResponse));
    }

    public Mono<ServerResponse> deleteCustomer(ServerRequest request) {
        return this.customerService.deleteCustomer(this.customerId(request))
                .then(ServerResponse.noContent().build());
    }

    private long customerId(ServerRequest request) {
        return Long.parseLong(request.pathVariable("customerId"));
    }
}
````

### 🔍 Helper privado `customerId(...)`

El método `customerId(...)` centraliza la extracción del path variable para no repetir:

````bash
Long.parseLong(request.pathVariable("customerId"))
````

> ⚠️ **Nota:**
> - El `RouterFunction` garantiza que el path variable `{customerId}` **existe** (si no existiera, el router retorna un
    `404` antes de llegar al handler).
> - Pero `no garantiza` que sea un valor numérico válido.
> - Una petición como `PUT /api/v1/customers/abc` llegaría al handler y lanzaría un `NumberFormatException`, que debe
    ser manejado por un `WebExceptionHandler` global.

### 🔄 El operador `.as()`

El método `allCustomers()` utiliza el operador `.as()`. Este operador es básicamente una **transformación de nivel
superior**. Su firma para un publisher del tipo flux es:

````bash
public final <P> P as(Function<? super Flux<T>, P> transformer)
````

- Recibe el `Flux<T>` como argumento de una función transformadora, permitiéndote operar sobre él de forma directa.
- Retorna lo que esa función devuelva, que puede ser cualquier tipo `P`, no necesariamente otro `Flux` o `Mono`.
- El `P` se `infiere automáticamente` por el compilador según lo que retorne la función lambda que le pasemos.

Ejemplo en nuestro caso:

````bash
.as(customerResponseFlux ->
    ServerResponse.ok().body(customerResponseFlux, CustomerResponse.class))
//  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//  Esto retorna Mono<ServerResponse>, entonces P = Mono<ServerResponse>
````

👉 Como `ServerResponse.ok().body(...)` retorna `Mono<ServerResponse>`, el compilador infiere que
`P = Mono<ServerResponse>`. De esta forma, el método `allCustomers()` puede retornar directamente
`Mono<ServerResponse>`.

### 📌 Equivalente sin `.as()`

El mismo código podría escribirse sin `.as()`:

````java
public Mono<ServerResponse> allCustomers(ServerRequest request) {
    Flux<CustomerResponse> flux = this.customerService.getAllCustomers();
    return ServerResponse.ok().body(flux, CustomerResponse.class);
}
````

- `.as()` simplemente permite mantener un estilo fluent/encadenado sin romper la cadena de operadores reactivos.
- Tanto `Flux` como `Mono` tienen su propio `.as()` con el mismo principio.

## 📘 Configuración de rutas funcionales (Functional Endpoints)

Como dijimos hace dos lecciones, la clase `CustomerRouter` es equivalente a una clase anotada con `@RestController`:  
aquí **solo se definen las rutas**.

La diferencia es que en lugar de usar anotaciones como `@GetMapping` o `@PostMapping`, declaramos las rutas de forma
**funcional y explícita**.

### 🎯 Objetivo

En esta clase establecemos las rutas `HTTP` básicas (`GET`, `POST`, `PUT`, `DELETE`) aplicando una separación clara
entre:

- **Definición de rutas** → responsabilidad de `CustomerRouter`.
- **Lógica de manejo** → responsabilidad de `CustomerHandler`.

Además, se utiliza una constante base `CUSTOMERS_URI` para asegurar consistencia y evitar duplicación de cadenas de
texto en la definición de rutas.

### ✅ Beneficios de esta estrategia

- 📑 **Facilita el mantenimiento y la refactorización** del código.
- 👀 **Mejora la legibilidad y claridad** de las rutas definidas.
- 🧩 **Buenas prácticas de nombramiento semántico**, evitando cadenas mágicas repetidas.

### 🧱 Clase `CustomerRouter`

````java

@Configuration
public class CustomerRouter {

    private static final String CUSTOMERS_URI = "/api/v1/customers";
    private static final String CUSTOMER_ID_PATH = "/{customerId}";

    @Bean
    public RouterFunction<ServerResponse> customerRoutes(CustomerHandler handler) {
        return RouterFunctions.route()
                .GET(CUSTOMERS_URI, handler::allCustomers)
                .GET(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::getCustomer)
                .POST(CUSTOMERS_URI, handler::saveCustomer)
                .PUT(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::updateCustomer)
                .DELETE(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::deleteCustomer)
                .build();
    }
}
````

#### 🔍 Explicación

- Constantes `CUSTOMERS_URI` y `CUSTOMER_ID_PATH`. Evitan duplicación de cadenas y aseguran consistencia en la
  definición de rutas.
- `RouterFunctions.route()`. Método builder que permite declarar las rutas de forma encadenada y explícita.
- Delegación a `CustomerHandler`. Cada ruta se asocia directamente a un método del handler (`handler::allCustomers`,
  `handler::getCustomer`, etc.).
- `.build()`. Finaliza la construcción del `RouterFunction` y lo expone como bean para que Spring lo registre en el
  contexto.

## ⚠️ Validación de Entradas / Manejador de Errores

En esta sección trabajamos el manejo de errores cuando un `handler function` emite una **señal de error**  
(es decir, un `Mono.error(...)`).

Esto es similar a lo que hacíamos con la clase anotada con `@RestControllerAdvice`, pero adaptado al enfoque funcional
con `RouterFunction` en `Spring WebFlux`.

### 🎯 Estrategia de manejo de errores

En este curso implementamos dos niveles de manejo:

1. **Manejo de errores a nivel de Router** → usando `.onError(...)` en `CustomerRouter`.
2. **Manejo de errores global** → mediante una clase que extiende `AbstractErrorWebExceptionHandler`.

De esta forma, capturamos tanto excepciones específicas como aquellas que no estén contempladas en el router.

### 🧩 Manejador de Excepciones Personalizado

La clase `CustomerExceptionHandler` implementa métodos que retornan un `ServerResponse` con la excepción envuelta en un
**ProblemDetail** (formato estándar de errores HTTP definido por **RFC 7807**).

Para evitar duplicación de código, se crea un método privado `buildResponse(...)` que encapsula la lógica común y recibe
un `Consumer<ProblemDetail>` para personalizar cada caso.

````java

@Slf4j
@Component
public class CustomerExceptionHandler {
    public Mono<ServerResponse> handleNotFoundException(CustomerNotFoundException ex, ServerRequest request) {
        log.error(ex.getMessage());

        return this.buildResponse(HttpStatus.NOT_FOUND, ex, request, problemDetail -> {
            problemDetail.setType(URI.create("https://example.com/problems/customer-not-found"));
            problemDetail.setTitle("Cliente no encontrado");
        });
    }

    public Mono<ServerResponse> handleInvalidInputException(InvalidInputException ex, ServerRequest request) {
        log.error(ex.getMessage());

        return this.buildResponse(HttpStatus.BAD_REQUEST, ex, request, problemDetail -> {
            problemDetail.setType(URI.create("https://example.com/problems/invalid-input"));
            problemDetail.setTitle("Entrada no válida");
        });
    }

    private Mono<ServerResponse> buildResponse(HttpStatus status, Exception ex, ServerRequest request,
                                               Consumer<ProblemDetail> problemDetailConsumer) {
        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(status, ex.getMessage());
        problemDetail.setInstance(URI.create(request.path()));

        problemDetailConsumer.accept(problemDetail);

        return ServerResponse
                .status(status)
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .bodyValue(problemDetail);
    }
}
````

### 🛣️ Manejo de errores a nivel de Router

En `CustomerRouter` inyectamos el `CustomerExceptionHandler` y usamos `.onError(...)` para asociar cada tipo
de excepción con su manejador.

````java

@RequiredArgsConstructor
@Configuration
public class CustomerRouter {

    private static final String CUSTOMERS_URI = "/api/v1/customers";
    private static final String CUSTOMER_ID_PATH = "/{customerId}";

    private final CustomerExceptionHandler customerExceptionHandler;

    @Bean
    public RouterFunction<ServerResponse> customerRoutes(CustomerHandler handler) {
        return RouterFunctions.route()
                .GET(CUSTOMERS_URI, handler::allCustomers)
                .GET(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::getCustomer)
                .POST(CUSTOMERS_URI, handler::saveCustomer)
                .PUT(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::updateCustomer)
                .DELETE(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::deleteCustomer)
                .onError(CustomerNotFoundException.class, this.customerExceptionHandler::handleNotFoundException)
                .onError(InvalidInputException.class, this.customerExceptionHandler::handleInvalidInputException)
                .build();
    }
}
````

#### 🔎 ¿Qué es `.onError(...)` en el Router?

- `Propio del RouterFunction`:
    - Este método no pertenece a `Flux` ni `Mono` como `onErrorResume` o `onErrorReturn`.
    - Es parte del `builder` de rutas funcionales `(RouterFunctions.route())`, y su propósito es asociar un tipo de
      excepción con un manejador específico.
- `Funciona como un "catch" declarativo`:
    - Cuando un `HandlerFunction` lanza una excepción (por ejemplo, `Mono.error(new CustomerNotFoundException(...))`),
      el router intercepta esa señal de error y redirige la ejecución al manejador que definimos con `.onError(...)`.
- Diferencia con operadores reactivos (`onErrorResume`, `onErrorReturn`):
    - `onErrorResume` y `onErrorReturn` son operadores de reactores `(Flux/Mono)`, usados dentro de un flujo reactivo
      para recuperar o transformar un error.
    - `.onError(...)` en el router es un mapeo de excepciones a handlers a nivel de enrutamiento, no dentro del flujo
      de datos.
    - Es decir, en lugar de manejar el error dentro del `Mono` o `Flux`, lo manejamos en el pipeline de enrutamiento.
- `Firma simplificada`:
    ````java
    <T extends Throwable> Builder onError(Class<T> exceptionType,
                                          BiFunction<T, ServerRequest, Mono<ServerResponse>> handler);
    ````
    - `exceptionType`: la clase de la excepción que queremos capturar.
    - `handler`: función que recibe la excepción y el `ServerRequest`, y retorna un `Mono<ServerResponse>` con la
      respuesta adecuada.

👉 En resumen:
> `.onError(...)` es un mecanismo propio del router para capturar excepciones y redirigirlas a un manejador de errores,
> funcionando como un “catch declarativo” a nivel de enrutamiento. No reemplaza a `onErrorResume` o `onErrorReturn`,
> sino que complementa el manejo de errores en el contexto de functional endpoints.

### 🌐 Manejo de errores global

La clase `GlobalErrorHandler` extiende `AbstractErrorWebExceptionHandler` y captura excepciones no manejadas en
el router. Se registra una única ruta comodín que delega a un método central, el cual decide qué handler específico
invocar según el tipo de excepción.

````java

@Slf4j
@Order(-2)
@Component
public class GlobalErrorHandler extends AbstractErrorWebExceptionHandler {

    // Spring inyecta tod esto automáticamente
    public GlobalErrorHandler(ErrorAttributes errorAttributes,
                              WebProperties webProperties,
                              ApplicationContext applicationContext,
                              ServerCodecConfigurer configurer) {
        super(errorAttributes, webProperties.getResources(), applicationContext);

        // necesario para que Spring sepa cómo serializar las respuestas
        super.setMessageWriters(configurer.getWriters());
        super.setMessageReaders(configurer.getReaders());
    }

    @Override
    protected RouterFunction<ServerResponse> getRoutingFunction(ErrorAttributes errorAttributes) {
        return RouterFunctions.route(RequestPredicates.all(), this::handleAllErrors);
    }

    private Mono<ServerResponse> handleAllErrors(ServerRequest request) {
        Throwable throwable = this.getError(request);
        return switch (throwable) {
            case NumberFormatException ex -> this.handleNumberFormatException(ex, request);
            default -> this.handleGenericException(throwable, request);
        };
    }

    private Mono<ServerResponse> handleNumberFormatException(NumberFormatException ex, ServerRequest request) {
        log.error(ex.getMessage());

        return this.buildResponse(HttpStatus.BAD_REQUEST, ex, request, problemDetail -> {
            problemDetail.setType(URI.create("https://example.com/problems/invalid-number-format"));
            problemDetail.setDetail("Se esperaba un valor numérico pero se recibió un valor no válido");
            problemDetail.setTitle("Entrada no válida");
        });
    }

    private Mono<ServerResponse> handleGenericException(Throwable ex, ServerRequest request) {
        log.error("Excepción no controlada en [{}]", request.path(), ex);

        return this.buildResponse(HttpStatus.INTERNAL_SERVER_ERROR, ex, request, problemDetail -> {
            problemDetail.setType(URI.create("https://example.com/problems/internal-error"));
            problemDetail.setTitle("Internal Server Error");
        });
    }

    private Mono<ServerResponse> buildResponse(HttpStatus status, Throwable ex, ServerRequest request,
                                               Consumer<ProblemDetail> problemDetailConsumer) {
        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(status, ex.getMessage());
        problemDetail.setInstance(URI.create(request.path()));

        problemDetailConsumer.accept(problemDetail);

        return ServerResponse
                .status(status)
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .bodyValue(problemDetail);
    }
}
````

#### 📌 ¿Por qué extender `AbstractErrorWebExceptionHandler`?

`Spring WebFlux` ya trae un manejador de errores por defecto, pero si queremos personalizar las respuestas globales
(por ejemplo, devolver un `ProblemDetail` en lugar de un `JSON genérico`), necesitamos sobrescribir ese comportamiento.
La clase `AbstractErrorWebExceptionHandler` es la base que Spring ofrece para construir un error handler global en
aplicaciones `WebFlux`.

#### 📌 Analizando código

- `@Order(-2)` → define la prioridad de este manejador.
    - Spring tiene su propio `DefaultErrorWebExceptionHandler` con orden `-1`.
    - Al poner `-2`, nuestro handler se ejecuta antes que el de Spring, asegurando que nuestras respuestas
      personalizadas tengan prioridad.
- `Constructor`: Parámetros inyectados automáticamente por Spring.
    - `ErrorAttributes` → metadatos del error (mensaje, timestamp, etc.).
    - `WebProperties` → configuración web de la aplicación.
    - `ApplicationContext` → acceso al contexto de Spring.
    - `ServerCodecConfigurer` → define cómo serializar y deserializar las respuestas (codecs).

👉 **Sí, es cierto: Spring inyecta todo esto automáticamente en el constructor.**

- `super(...)` → inicializa la clase base con los atributos necesarios.
- `setMessageWriters` y `setMessageReaders` → muy importantes:
    - Indican a Spring cómo serializar las respuestas (JSON, ProblemDetail, etc.).
    - Si no configuramos esto, Spring no sabría cómo convertir nuestro `ProblemDetail` en JSON y devolverlo al cliente.
    - En la práctica, sin estos setters, obtendríamos errores de serialización o respuestas vacías.


- Método principal: `getRoutingFunction(...)`
    - Este método define **cómo se enrutan las excepciones globales.**
    - `AbstractErrorWebExceptionHandler` requiere obligatoriamente al menos una ruta registrada con `GET()`,
      `POST()`, etc. Sin ella, el builder lanza un `IllegalStateException` al arrancar.
    - Sin embargo, en lugar de registrar una ruta por cada método HTTP (`GET("/**")`, `POST("/**")`,
      `PUT("/**")`, etc.), se usa `RequestPredicates.all()` como predicado comodín único que acepta cualquier método
      HTTP y cualquier path.
    - Toda petición de error es delegada al método `handleAllErrors(...)`, que centraliza la decisión de qué handler
      invocar según el tipo de excepción.
- Método `handleAllErrors(...)`
    - Recupera la excepción almacenada por Spring mediante `this.getError(request)`.
    - Usa un `switch` con **pattern matching (Java 21+)** para despachar al handler específico según el tipo
      de excepción:
        - `NumberFormatException` → errores de conversión numérica (ejemplo: `GET /customers/abc`).
        - `default` → cualquier otra excepción no controlada.
    - Es preferible al encadenamiento de `if/instanceof` porque es más legible y evita casteos manuales.

#### 📌 En resumen

- Extendemos `AbstractErrorWebExceptionHandler` para personalizar el manejo global de errores en WebFlux.
- `@Order(-2)` asegura que nuestro handler se ejecute antes que el default de Spring.
- `Constructor con codecs` garantiza que las respuestas se serialicen correctamente.
- `getRoutingFunction(...)` registra una única ruta comodín con `RequestPredicates.all()`.
- `handleAllErrors(...)` centraliza el despacho usando `switch` con pattern matching.
- `Métodos específicos` + `buildResponse` permiten devolver errores consistentes en formato `ProblemDetail`.

### 💡 Con esto nuestra documentación cubre dos niveles de manejo de errores

- `Router-specific` con `.onError(...)`.
- `Global` con `AbstractErrorWebExceptionHandler`.

## 🧪 Probando Validación de Entradas con `.onError(...)`

Una vez configurado el `CustomerExceptionHandler` y las reglas de `.onError(...)` en el `CustomerRouter`, verificamos

### ❌ Cliente no existe

````bash
$ curl -v http://localhost:8080/api/v1/customers/99 | jq
````

## 📘 Resultados Paginados

En esta sección implementamos la **paginación de clientes** utilizando `RouterFunction`.  
La paginación es una técnica que permite dividir grandes volúmenes de datos en **bloques o páginas**,
facilitando el consumo de información y evitando sobrecargar al cliente o al servidor.

### 🛠️ Handler para resultados paginados

En la clase `CustomerHandler` se agregaron dos métodos:

- **Paginación simple (`getSimplePaginationCustomers`)**
    - Retorna únicamente la lista de clientes correspondiente a la página solicitada.
    - Si no se especifican parámetros, se usan valores por defecto: `page = 0` y `size = 5`.

- **Paginación avanzada (`getAdvancedPaginationCustomers`)**
    - Retorna un objeto `Page<CustomerResponse>` que incluye tanto los clientes como los **metadatos de paginación**
      (total de páginas, número de elementos, etc.), ideal para interfaces más completas.

Ambos métodos utilizan un helper privado `getIntQueryParam(...)` para extraer parámetros de la query string y evitar
duplicar código.

````java

@Slf4j
@RequiredArgsConstructor
@Component
public class CustomerHandler {

    private final CustomerService customerService;

    public Mono<ServerResponse> getSimplePaginationCustomers(ServerRequest request) {
        Integer pageNumber = this.getIntQueryParam(request, "page", 0);
        Integer pageSize = this.getIntQueryParam(request, "size", 5);
        return this.customerService.getAllCustomers(pageNumber, pageSize)
                .collectList()
                .flatMap(customerResponseList ->
                        ServerResponse.ok().bodyValue(customerResponseList));
    }

    public Mono<ServerResponse> getAdvancedPaginationCustomers(ServerRequest request) {
        Integer pageNumber = this.getIntQueryParam(request, "page", 0);
        Integer pageSize = this.getIntQueryParam(request, "size", 5);
        return this.customerService.getAllCustomers(PageRequest.of(pageNumber, pageSize))
                .flatMap(customerResponsePage ->
                        ServerResponse.ok().bodyValue(customerResponsePage));
    }

    /* other methods */

    private Integer getIntQueryParam(ServerRequest request, String param, int defaultValue) {
        return request.queryParam(param)
                .map(Integer::parseInt)
                .orElse(defaultValue);
    }
}
````

> 💡 `Ventaja`: este enfoque permite que los clientes consuman datos en bloques, reduciendo el tiempo de respuesta
> y mejorando la experiencia de usuario.

### 🌐 Definición de las rutas

En la clase `CustomerRouter` se añadieron dos rutas específicas para exponer los métodos de paginación:

- 📋 **Paginación simple:** `/api/v1/customers/simple-pagination`
- 📊 **Paginación avanzada:** `/api/v1/customers/advanced-pagination`

````java

@RequiredArgsConstructor
@Configuration
public class CustomerRouter {

    private static final String CUSTOMERS_URI = "/api/v1/customers";
    private static final String CUSTOMER_ID_PATH = "/{customerId}";

    private final CustomerExceptionHandler customerExceptionHandler;

    @Bean
    public RouterFunction<ServerResponse> customerRoutes(CustomerHandler handler) {
        return RouterFunctions.route()
                .GET(CUSTOMERS_URI, handler::allCustomers)
                .GET(CUSTOMERS_URI + "/simple-pagination", handler::getSimplePaginationCustomers)
                .GET(CUSTOMERS_URI + "/advanced-pagination", handler::getAdvancedPaginationCustomers)
                .GET(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::getCustomer)
                .POST(CUSTOMERS_URI, handler::saveCustomer)
                .PUT(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::updateCustomer)
                .DELETE(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::deleteCustomer)
                .onError(CustomerNotFoundException.class, this.customerExceptionHandler::handleNotFoundException)
                .onError(InvalidInputException.class, this.customerExceptionHandler::handleInvalidInputException)
                .build();
    }
}
````

#### 📌 Conclusión

- La paginación simple devuelve únicamente la lista de clientes.
- La paginación avanzada devuelve además metadatos útiles para construir interfaces más completas.
- Ambas rutas están integradas en el `CustomerRouter`, manteniendo la coherencia con el resto de endpoints CRUD.
- Este patrón mejora la eficiencia y escalabilidad de la API, ofreciendo una experiencia más fluida a los consumidores.

## 🧭 Orden de las Rutas en Functional Endpoints

Cuando definimos rutas en una aplicación basada en funciones con **Spring WebFlux**, el **orden en que se registran las
rutas es crítico**. A diferencia de los controladores tradicionales con `@RestController`, aquí el enrutamiento es
**funcional y secuencial**: Spring evalúa las rutas en el orden en que fueron agregadas,
y **la primera coincidencia gana**.

### 📋 Ejemplo de RouterFunction

Así hemos venido construyendo nuestro `CustomerRouter`:

````java

@RequiredArgsConstructor
@Configuration
public class CustomerRouter {

    private static final String CUSTOMERS_URI = "/api/v1/customers";
    private static final String CUSTOMER_ID_PATH = "/{customerId}";

    private final CustomerExceptionHandler customerExceptionHandler;

    @Bean
    public RouterFunction<ServerResponse> customerRoutes(CustomerHandler handler) {
        return RouterFunctions.route()
                .GET(CUSTOMERS_URI, handler::allCustomers)
                .GET(CUSTOMERS_URI + "/simple-pagination", handler::getSimplePaginationCustomers)
                .GET(CUSTOMERS_URI + "/advanced-pagination", handler::getAdvancedPaginationCustomers)
                .GET(CUSTOMERS_URI + CUSTOMER_ID_PATH, handler::getCustomer)
                /*... other routes ...*/
                .build();
    }
}
````

### ⚠️ Posible conflicto

Observemos estas dos rutas:

````bash
.GET("/api/v1/customers/simple-pagination", handler::getSimplePaginationCustomers)
.GET("/api/v1/customers/{customerId}", handler::getCustomer)
````

Ambas comparten el prefijo `/api/v1/customers`, pero una es estática y específica (`/simple-pagination`) y la otra
es dinámica (`/{customerId}`).

Si invertimos el orden:

````bash
.GET("/api/v1/customers/{customerId}", handler::getCustomer)
.GET("/api/v1/customers/simple-pagination", handler::getSimplePaginationCustomers)
````

Una petición como:

````bash
GET /api/v1/customers/simple-pagination
````

Será interpretada por Spring como si `simple-pagination` fuera un `customerId`.  
👉 `Resultado`: se invoca el handler incorrecto (`getCustomer(...)`), generando errores en la respuesta.

### ✅ ¿Cómo evitarlo?

La regla es sencilla:

- **Primero registrar rutas más específicas (estáticas).**
- **Después registrar rutas genéricas o dinámicas.**

Orden correcto:

````bash
.GET("/api/v1/customers/simple-pagination", handler::getSimplePaginationCustomers)
.GET("/api/v1/customers/{customerId}", handler::getCustomer)
````

### 🔎 Diferencia con `@RestController`

- Con `@RestController` → `El orden no importa`, Spring se encarga de resolver las rutas.
- Con `RouterFunction` → El orden `sí importa`, porque tú defines manualmente el flujo de resolución.

### 🧠 Conclusión

- El enrutamiento funcional en WebFlux es secuencial: la primera coincidencia gana.
- Siempre define primero las rutas más específicas y luego las dinámicas.
- Este detalle es clave para evitar ambigüedades y garantizar que cada petición llegue al handler correcto.
