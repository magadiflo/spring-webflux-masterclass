## 🧠 Introducción

`Spring WebFlux` incluye un `cliente HTTP no bloqueante` llamado `WebClient`, el cual forma parte de su stack reactivo.
Este cliente proporciona una **API fluida y funcional**, construida sobre el motor `Reactor`, permitiendo componer
lógica asíncrona de manera declarativa sin gestionar explícitamente subprocesos o sincronización.

`WebClient` es:

- Completamente `no bloqueante`.
- Compatible con `streaming` de datos.
- Utiliza los mismos códecs que el lado del servidor (por ejemplo, `Jackson`, `JAXB`, etc.) para `codificar/decodificar`
  el contenido de las `solicitudes` y `respuestas`.

Para funcionar, `WebClient` necesita una `biblioteca cliente HTTP` subyacente. `Spring` ofrece soporte integrado para
varios conectores:

- `Reactor Netty` (por defecto)
- JDK HttpClient
- Jetty Reactive HttpClient
- Apache HttpComponents
- Además, es posible registrar otros conectores mediante un `ClientHttpConnector` personalizado.

### 🔍 Características clave de WebClient

- API fluida, basada en Reactor.
- Cliente `no bloqueante` para enviar solicitudes y procesar respuestas HTTP.
- Construido sobre `reactor-netty`, aunque puedes sustituirlo por otros conectores.
- Una vez creado, el `WebClient` es `inmutable` y `seguro` para su uso en `múltiples hilos` (`thread-safe`).
- Permite la personalización de encabezados, autenticación, codificadores, interceptores, etc.
- Ideal para arquitecturas de **microservicios** y escenarios de **alta concurrencia**.

### 📊 Comparación rápida: RestTemplate vs WebClient

| Aspecto                | RestTemplate (clásico) | WebClient (reactivo)     |
|------------------------|------------------------|--------------------------|
| Naturaleza             | Bloqueante             | No bloqueante            |
| Modelo de programación | Imperativo             | Declarativo (Reactor)    |
| Concurrencia           | Limitada por hilos     | Escalable con event-loop |
| Streaming              | No soportado           | Soportado                |
| Estado                 | Mutable                | Inmutable, thread-safe   |

### 🧩 Caso de uso en nuestra aplicación

Supongamos que tenemos una aplicación principal llamada `our-app`, la cual necesita interactuar con dos servicios
externos:

- `order-service`
- `payment-service`

En una arquitectura de microservicios es común que un servicio consuma datos o desencadene acciones en otros.  
Para ello, definimos dos beans de `WebClient`, cada uno con una **URL base** para comunicarse con los servicios
externos.

📷 Código y diagrama referencial:

````java
// Create once, expose as a bean
@Bean
public WebClient orderClient() {
    return WebClient.builder()
            .baseUrl("http://order-service.com")
            .build();
}

@Bean
public WebClient paymentClient() {
    return WebClient.builder()
            .baseUrl("http://payment-service.com")
            .build();
}
````

````java
// Use  it everywhere
@Autowired
private WebClient orderClient;
````

### 🔁 Mutabilidad controlada

Aunque un `WebClient` `es inmutable una vez construido`, si necesitamos modificar algún aspecto de su configuración
(por ejemplo, agregar un `header`, cambiar el `timeout`, etc.), podemos hacerlo utilizando el método `.mutate()`. Esto
permite crear una copia modificada del `WebClient` original sin afectar su configuración base.

````java
WebClient originalClient = WebClient.builder()
        .baseUrl("http://order-service.com")
        .build();

WebClient modifiedClient = originalClient
        .mutate()
        .defaultHeader("Authorization", "Bearer token")
        .build();
````

### 🧠 Conclusión

- **WebClient** es el reemplazo moderno y reactivo de **RestTemplate.**
- Es **no bloqueante, thread-safe** e ideal para arquitecturas de microservicios.
- Permite configurar clientes con **baseUrl**, personalizar headers y mutar configuraciones sin perder inmutabilidad.
- Su integración con Reactor lo convierte en una herramienta poderosa para construir APIs escalables y eficientes.

### 🧩 Clase base: `AbstractWebClient`

````java

@Slf4j
abstract class AbstractWebClient {

    // Method genérico para imprimir cada item recibido en el flujo
    protected <T> Consumer<T> print() {
        return item -> log.info("recibido: {}", item);
    }

    // WebClient con configuración por defecto
    protected WebClient createWebClient() {
        return this.createWebClient(builder -> {
        });
    }

    // WebClient con posibilidad de personalización a través del consumidor
    protected WebClient createWebClient(Consumer<WebClient.Builder> consumer) {
        WebClient.Builder builder = WebClient.builder().baseUrl("http://localhost:7070/demo02");
        consumer.accept(builder);
        return builder.build();
    }
}
````

#### 📌 Explicación del código

- Método `print()`:
    - Utilitario genérico que imprime en logs cada elemento recibido en el flujo reactivo.
    - Útil para depurar y observar cómo llegan los datos desde el servicio externo.

- Método `createWebClient()` (por defecto):
    - Crea un `WebClient` con configuración básica y la URL base apuntando al servicio externo en
      `http://localhost:7070/demo02`.

- Método `createWebClient(Consumer<WebClient.Builder>)`:
    - Permite personalizar el cliente antes de construirlo (ej. agregar headers, configurar timeouts, etc.).
    - Esto nos da flexibilidad sin perder la simplicidad de tener una configuración común.

### 📡 Primera solicitud con WebClient

Vamos a realizar una solicitud simple de tipo `GET` utilizando `WebClient`.

> ⚠️ **Importante:**  
> No estamos escribiendo pruebas unitarias en sentido estricto. Estas clases de prueba son simplemente una manera
> rápida y práctica de experimentar con `WebClient`, observar su comportamiento y evitar crear controladores o
> servicios solo para pruebas.

````java
class Lec01MonoTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void simpleGet() throws InterruptedException {
        this.client.get()
                .uri("/lec01/product/{id}", 1)
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .subscribe();

        // Permite que la suscripción finalice antes de que termine el test
        Thread.sleep(Duration.ofSeconds(2));
    }
}
````

### Explicación

- `retrieve()` inicia la ejecución de la solicitud y espera una respuesta con cuerpo.
- `bodyToMono(Product.class)` indica que esperamos un solo objeto `Product` como resultado (por eso usamos `Mono`).
- `doOnNext(this.print())` imprime el resultado cuando llega la respuesta.
- `subscribe()` dispara la ejecución de la llamada asíncrona.
- `Thread.sleep(...)` se utiliza aquí como una manera simple (aunque no recomendable para producción) de evitar que el
  método termine antes de recibir la respuesta.
    - En un contexto real, usaríamos algo como `StepVerifier`, `block()` (solo en pruebas) o pruebas con
      `@SpringBootTest` para manejar este escenario correctamente.

## ⚡ Solicitudes concurrentes sin bloqueo

En este apartado vamos a demostrar cómo realizar **múltiples solicitudes concurrentes y no bloqueantes** utilizando
`WebClient`, una de las principales herramientas reactivas de **Spring WebFlux**.

### 🧠 Recordando algunos conceptos

- **WebClient** está basado en **Reactor Netty**, el cliente HTTP reactivo por defecto.
- **Reactor Netty**:
    - Utiliza un **modelo de un hilo por núcleo** (`1 hilo/CPU`).
    - Está diseñado para ser **no bloqueante**, es decir, no espera activamente por una respuesta, liberando recursos
      mientras tanto.

### 📡 Escenario de prueba

El endpoint externo `/lec01/product/{id}` tiene la siguiente descripción:

> "Proporcione los detalles del producto para el ID de producto indicado. Se admiten ID de producto entre 1 y 100.
> `Cada llamada tarda aproximadamente 1 segundo`."

📌 Esto significa que:

- Si ejecutáramos **100 solicitudes secuenciales y bloqueantes**, el tiempo total sería de ~100 segundos.
- Usando `WebClient` con suscripciones reactivas, todas las solicitudes se ejecutan **en paralelo**, y la respuesta
  total se obtiene en **1 a 2 segundos**.

### 🧩 Código de prueba

````java

class Lec01MonoTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void concurrentRequests() throws InterruptedException {
        for (int i = 1; i <= 100; i++) {
            this.client.get()
                    .uri("/lec01/product/{id}", i)
                    .retrieve()
                    .bodyToMono(Product.class)
                    .doOnNext(this.print())
                    .subscribe();
        }

        Thread.sleep(Duration.ofSeconds(2));
    }
}
````

### 📌 ¿Qué estamos demostrando?

En un modelo tradicional y bloqueante (ej. `RestTemplate`):

- Cada solicitud ocupa un hilo hasta recibir la respuesta.
- Los recursos quedan bloqueados, limitando la escalabilidad.

Con `WebClient` y `Reactor Netty`:

- ✅ Un solo hilo puede iniciar múltiples solicitudes concurrentemente.
- ✅ Mientras espera las respuestas, el hilo no se bloquea.
- ✅ Las respuestas llegan en paralelo y se manejan de forma asíncrona.
- ✅ Se logra alta escalabilidad con mínimo uso de recursos.

## 🌊 Streaming GET

En este apartado abordaremos el concepto de **respuesta en streaming** utilizando **Spring WebFlux**.  
Vamos a consumir un endpoint que retorna los datos de forma progresiva, es decir, como un **stream continuo**.

### 🧩 Características del servicio externo

El servicio expone un endpoint con las siguientes propiedades:

- 📦 Proporciona los detalles de productos, enviando una lista de **1 a 10 elementos**.
- ⏱️ Tiene un retraso de **500 ms** entre cada elemento emitido.
- 📝 El tipo de contenido (`media type`) de la respuesta es `text/event-stream`.

### 🎯 Objetivo

Queremos consumir esta respuesta en **streaming** usando un cliente reactivo (`WebClient`) y verificar que todos
los elementos se reciben correctamente. Para ello, evitaremos el uso de `Thread.sleep(...)` y en su lugar
utilizaremos **StepVerifier** para manejar la sincronización de forma reactiva.

### 🧪 Uso de StepVerifier

El siguiente ejemplo muestra cómo verificar la finalización completa del flujo con
`.as(StepVerifier::create).verifyComplete()`:

````java
class Lec02FluxTest extends AbstractWebClient {

    private final WebClient webClient = this.createWebClient();

    @Test
    void streamingResponse() {
        this.webClient.get()
                .uri("/lec02/product/stream")
                .accept(MediaType.TEXT_EVENT_STREAM) // Opcional
                .retrieve()
                .bodyToFlux(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}

````

#### 📌 Explicación:

- `.accept(MediaType.TEXT_EVENT_STREAM)` → envía el header `Accept: text/event-stream`. Ese header le dice al
  servidor qué tipo de respuesta esperas recibir.
    - No es obligatorio, ya que el servidor envía `Content-Type: text/event-stream`.
    - Sin embargo, `es recomendable declararlo` explícitamente en arquitecturas reactivas.
- `StepVerifier` → nos permite verificar la finalización del flujo sin introducir pausas artificiales.

> ⚠️ En el código anterior, no estamos validando valores específicos. Solo usamos `StepVerifier` para esperar
> la finalización del flujo y observar el comportamiento del endpoint en tiempo real.

### ⏹️ Cancelación del flujo con `.take(...)`

Uno de los beneficios del enfoque reactivo es que el cliente puede **cancelar la suscripción en cualquier momento.**
Esto lo logramos fácilmente con el operador `.take(...)`.

````java
class Lec02FluxTest extends AbstractWebClient {

    private final WebClient webClient = this.createWebClient();

    @Test
    void streamingResponse2() {
        this.webClient.get()
                .uri("/lec02/product/stream")
                .accept(MediaType.TEXT_EVENT_STREAM) // Opcional
                .retrieve()
                .bodyToFlux(Product.class)
                .take(Duration.ofSeconds(3)) // Cancelamos después de 3 segundos
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 Esto significa que `solo recibiremos los elementos emitidos durante los primeros 3 segundos`. Cualquier emisión
posterior será cancelada automáticamente.

- El tipo de contenido `text/event-stream` indica que se está utilizando `Server-Sent Events` (`SSE`), una técnica útil

- `bodyToFlux(...)` permite mapear cada fragmento de respuesta a una instancia del objeto `Product`, gestionando el

- `.doOnNext(...)` es útil para registrar o realizar acciones con cada elemento emitido, sin modificar el flujo.
- `.then()` convierte el `Flux<Product>` a un `Mono<Void>` que se completa cuando el flujo termina, permitiendo usar
  `StepVerifier` sin esperar valores.

## 📤 POST – `bodyValue(...)` vs `body(...)`

En este apartado vamos a analizar las diferencias entre los métodos `bodyValue(...)` y `body(...)` al realizar
una solicitud `POST` con **Spring WebFlux**.

### 🧩 Contexto del servicio externo

El servicio expone un endpoint que:

- 📥 Acepta solicitudes `POST` con datos de productos.
- ⏱️ Tiene un retraso aproximado de **1 segundo** en responder.
- 🔄 Retorna el mismo objeto `Product` como respuesta (posiblemente con un ID generado).

### ✅ Envío con `bodyValue(...)`

Cuando ya tenemos el objeto en memoria y queremos enviarlo tal cual, usamos `bodyValue(...)`.  
Este método es ideal cuando el cuerpo de la solicitud es una **instancia concreta (no reactiva)**.

```java
class Lec03PostTest extends AbstractWebClient {

    private final WebClient webClient = this.createWebClient();

    @Test
    void postBodyValue() {
        Product product = new Product(null, "Monitor", 200);
        this.webClient.post()
                .uri("/lec03/product")
                .bodyValue(product)// El objeto ya está disponible en memoria
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

#### 📌 Explicación:

- El objeto `product` ya está construido en memoria.
- `bodyValue(...)` lo serializa directamente en el cuerpo de la solicitud.
- Es el enfoque más directo y común para enviar datos en un `POST`.

### 🔄 Envío con `body(...)`

En algunos casos, los datos no están disponibles de forma inmediata. Podemos generarlos de manera asíncrona o
recibirlos desde otra fuente reactiva (ej. base de datos, servicio externo).  
Para estos escenarios usamos `body(...)`, que permite enviar un `Publisher`.

````java
class Lec03PostTest extends AbstractWebClient {

    private final WebClient webClient = this.createWebClient();

    @Test
    void postBody() {
        Mono<Product> productMono = Mono.fromSupplier(() -> new Product(null, "Monitor", 200))
                .delayElement(Duration.ofSeconds(1)); // Simula retraso en la generación del dato
        this.webClient.post()
                .uri("/lec03/product")
                .body(productMono, Product.class) // Se pasa el publisher
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

#### 📌 Explicación

- Simulamos la creación del producto con un retraso de **1 segundo.**
- `body(...)` recibe un `Publisher<T>` y la clase `T` para que `WebClient` sepa cómo serializar el flujo emitido.
- Este método es más **flexible y reactivo**, ideal cuando los datos provienen de una cadena reactiva o no están
  disponibles inmediatamente.

### 💡 Recomendaciones

- Usa `bodyValue(...)` cuando los datos ya están disponibles en memoria y quieres enviarlos directamente.
- Usa `body(...)` cuando trabajes en un flujo completamente reactivo o cuando los datos se obtengan de forma
  asincrónica.
- Ambos métodos son válidos, pero elegir el correcto depende del contexto de disponibilidad de los datos.

## 🛠️ Configuración y anulación de headers por defecto en WebClient

En esta sección aprenderemos cómo **configurar cabeceras predeterminadas (default headers)** en `WebClient`,
y cómo **anularlas cuando sea necesario**. Esto es útil cuando ciertos endpoints requieren una cabecera obligatoria,
como identificadores de servicio, tokens, etc.

### 📡 Escenario del endpoint

Nuestro servicio externo expone un endpoint que:

- Devuelve los detalles de un producto según el ID (entre 1 y 100).
- Requiere obligatoriamente el header `caller-id`.
- Ejemplo: `caller-id: order-service`.

### ❌ Petición sin headers: Falla esperada

Ejecutemos la siguiente prueba, donde esperamos recibir el error **400 Bad Request**:

```java
class Lec04HeaderTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void defaultHeader() {
        this.client.get()
                .uri("/lec04/product/{id}", 1)
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 Resultado esperado:

````bash
java.lang.AssertionError: expectation "expectComplete" failed (expected: onComplete(); actual: onError(org.springframework.web.reactive.function.client.WebClientResponseException$BadRequest: 400 Bad Request from GET http://localhost:7070/demo02/lec04/product/1))
Error has been observed at the following site(s):
	*__checkpoint ⇢ 400 BAD_REQUEST from GET http://localhost:7070/demo02/lec04/product/1 [DefaultWebClient]
````

El error ocurre porque el endpoint espera recibir el header `caller-id` y nosotros no lo hemos enviado.

### ✅ Establecer cabecera por defecto

Podemos solucionar este problema configurando el `WebClient` para que incluya automáticamente la cabecera en todas las
solicitudes:

````java
class Lec04HeaderTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient(builder -> {
        builder.defaultHeader("caller-id", "order-service");
    });

    @Test
    void defaultHeader() {
        this.client.get()
                .uri("/lec04/product/{id}", 1)
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 Ahora cada vez que usemos `client`, la cabecera `caller-id` se enviará automáticamente:

````bash
10:57:21.422 [reactor-http-nio-2] INFO dev.magadiflo.app.sec09.AbstractWebClient -- recibido: Product[id=1, description=product-1, price=525]
````

### 📌 ¿Cuándo usar `defaultHeader(...)`?

- Cuando un encabezado debe estar presente en **todas o casi todas las peticiones.**
- Para evitar repetir manualmente `.header(...)` en cada solicitud.
- Para garantizar que un microservicio se identifique consistentemente (ej. `"caller-id": "order-service"`).

### 🔄 Anulación de encabezados predeterminados

También es común que necesitemos **sobrescribir** los headers en situaciones específicas.

📌 Escenario:

- Normalmente, todas nuestras peticiones deberán llevar el header `caller-id: order-service`.
- Pero, tenemos una solicitud muy específica donde queremos enviar el mismo header pero con otro valor
  `caller-id: new-service`.

````java
class Lec04HeaderTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient(builder -> {
        builder.defaultHeader("caller-id", "order-service");
    });

    @Test
    void overrideHeader() {
        this.client.get()
                .uri("/lec04/product/{id}", 1)
                .header("caller-id", "new-service") // sobrescribe el valor
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 Resultado:

````bash
11:00:33.601 [reactor-http-nio-2] INFO dev.magadiflo.app.sec09.AbstractWebClient -- recibido: Product[id=1, description=product-1, price=208]
````

### ¿Cómo funciona esto internamente?

- El `WebClient` primero carga los headers configurados por defecto.
- Luego, los `headers` definidos directamente en la solicitud (`.header(...)`) tienen prioridad.
- Si hay colisión en una clave, se usa el valor proporcionado directamente en la llamada.

### 📦 Envío de múltiples headers con un `Map`

En ocasiones, puede ser necesario enviar varios encabezados HTTP en una misma solicitud.
Para ello, `WebClient` permite usar un `Map<String, String>` y aplicarlo con `.headers(...)`.

````java
class Lec04HeaderTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient(builder -> {
        builder.defaultHeader("caller-id", "order-service");
    });

    @Test
    void headersWithMap() {
        var values = Map.of(
                "caller-id", "product-value",
                "some-key", "some-value"
        );
        this.client.get()
                .uri("/lec04/product/{id}", 1)
                .headers(httpHeaders -> httpHeaders.setAll(values)) // aplica todos los headers del map
                .retrieve()
                .bodyToMono(Product.class)
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 En este caso:

- Se sobrescribe el `caller-id` con `product-value`.
- Se agrega un nuevo encabezado: `"some-key": "some-value"`.
- `.headers(...)` permite modificar directamente los `HttpHeaders` de la solicitud.

### 🧠 Conclusión

- `defaultHeader(...)` es útil para **headers comunes y obligatorios** en todas las peticiones.
- `.header(...)` permite sobrescribir valores puntuales cuando sea necesario.
- `.headers(...)` con un Map facilita el envío de múltiples encabezados dinámicamente.
- Con estas técnicas, `WebClient` ofrece un manejo flexible y eficiente de headers HTTP en arquitecturas reactivas.

## 🚨 Servicio remoto - Manejo de errores

En esta sección abordaremos cómo manejar errores que pueden ocurrir al consumir un servicio remoto mediante
`WebClient`. Aprenderemos a **capturar respuestas de error** y a proporcionar una **respuesta predeterminada**
en caso de fallo.

### 📡 Descripción del servicio remoto

Trabajaremos con un endpoint que realiza operaciones matemáticas básicas. El servicio:

- Requiere dos parámetros numéricos (**ambos mayores que cero**).
- Espera una operación matemática como encabezado HTTP (`+`, `-`, `*`, `/`), con el nombre del header `operation`.
- Devuelve un objeto con el resultado de la operación.

### 🗂️ DTO: Representación del resultado

Creamos un record llamado `Calculator` que representa tanto la solicitud como la respuesta esperada del servicio remoto:

```java
public record Calculator(Integer first,
                         Integer second,
                         String operation,
                         Double result) {
}
````

### 🛑 Manejo básico de errores con `onErrorReturn(...)`

Si el cliente realiza una solicitud inválida (ej. operador no reconocido), el servicio remoto responderá con un error
(`400` o `500`). Podemos usar `onErrorReturn(...)` para devolver un objeto por defecto y evitar que el flujo falle.

````java

@Slf4j
class Lec05ErrorResponseTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void handlingError() {
        this.client.get()
                .uri("/lec05/calculator/{first}/{second}", 10, 20)
                .header("operation", "@") // operación inválida
                .retrieve()
                .bodyToMono(Calculator.class)
                .onErrorReturn(new Calculator(0, 0, null, 0D)) // respuesta por defecto
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

**¿Qué hace este código?**

- Envía una solicitud GET al endpoint `/lec05/calculator/10/20`.
- Incluye un encabezado inválido (`operation: @`), lo cual provocará un error del servidor.
- Al fallar la solicitud, se captura el error con `.onErrorReturn(...)`.
- Se devuelve un `Calculator` con valores por defecto (útil para seguir el flujo sin lanzar excepciones).

📌 Resultado:

````bash
11:45:50.848 [reactor-http-nio-2] INFO dev.magadiflo.app.sec09.AbstractWebClient -- recibido: Calculator[first=0, second=0, operation=null, result=0.0]
````

#### Consideraciones

- `onErrorReturn(...)` es útil para flujos simples donde no se necesita una lógica más sofisticada.
- Para casos más avanzados, se puede usar `.onErrorResume(...)`, que permite manejar distintos tipos de error y
  retornar diferentes flujos.
- También es posible acceder a detalles del error como el código HTTP y el body de la respuesta si se desea una lógica
  de recuperación más elaborada.

### 🛑 Manejo de errores según el tipo de excepción

Podemos retornar diferentes respuestas por defecto dependiendo del tipo de error HTTP recibido.
Para ello, usamos la sobrecarga de `onErrorReturn(...)` que acepta una clase de excepción como primer parámetro.

````java

@Slf4j
class Lec05ErrorResponseTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void handlingErrorWithSpecificException() {
        this.client.get()
                .uri("/lec05/calculator/{first}/{second}", 10, 20)
                .header("operation", "@")
                .retrieve()
                .bodyToMono(Calculator.class)
                .onErrorReturn(WebClientResponseException.InternalServerError.class, new Calculator(0, 0, null, 0D))
                .onErrorReturn(WebClientResponseException.BadRequest.class, new Calculator(0, 0, null, -1D))
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}
````

📌 Explicación:

- Si ocurre un `500 Internal Server Error`, devolvemos un objeto con resultado `0D`.
- Si ocurre un `400 Bad Request`, devolvemos un objeto con resultado `-1D`.
- Si ocurre otro error (ej. `404 Not Found`), el flujo fallará normalmente.

📌 Resultado:

````bash
11:56:18.012 [reactor-http-nio-2] INFO dev.magadiflo.app.sec09.AbstractWebClient -- recibido: Calculator[first=0, second=0, operation=null, result=-1.0]
````

### 🛑 Manejo de errores con `ProblemDetail` y `WebClientResponseException`

Cuando el servidor remoto devuelve un error estructurado como `application/problem+json`, podemos capturarlo y
loguearlo usando:

````java

@Slf4j
class Lec05ErrorResponseTest extends AbstractWebClient {

    private final WebClient client = this.createWebClient();

    @Test
    void handlingErrorWithDoOnError() {
        this.client.get()
                .uri("/lec05/calculator/{first}/{second}", 10, 20)
                .header("operation", "@")
                .retrieve()
                .bodyToMono(Calculator.class)
                .doOnError(WebClientResponseException.class, e -> {
                    log.error("{}", e.getResponseBodyAs(ProblemDetail.class));
                })
                .onErrorReturn(WebClientResponseException.InternalServerError.class, new Calculator(0, 0, null, 0D))
                .onErrorReturn(WebClientResponseException.BadRequest.class, new Calculator(0, 0, null, -1D))
                .doOnNext(this.print())
                .then()
                .as(StepVerifier::create)
                .verifyComplete();
    }
}

````

📌 Ejemplo de salida:

````bash
12:51:09.093 [reactor-http-nio-2] ERROR dev.magadiflo.app.sec09.Lec05ErrorResponseTest -- ProblemDetail[type='https://example.com/problems/bad-request', title='Bad Request', status=400, detail='operation header should be + - * /', instance='/demo02/lec05/calculator/10/20', properties='null']
12:51:09.099 [reactor-http-nio-2] INFO dev.magadiflo.app.sec09.AbstractWebClient -- recibido: Calculator[first=0, second=0, operation=null, result=-1.0]
````

### 🧠 Conclusión

- `onErrorReturn(...)` → útil para devolver un valor por defecto en caso de error simple.
- Sobrecarga con excepciones → permite manejar distintos tipos de error con respuestas diferenciadas.
- `doOnError(...)` + `ProblemDetail` → da visibilidad completa del error estructurado, ideal para auditoría y debugging.
- Con estas técnicas, `WebClient` ofrece un manejo de errores robusto y flexible, adaptado a distintos escenarios de
  servicios remotos.
